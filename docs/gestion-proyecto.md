# Gestión del proyecto

> Este documento define la estructura. El contenido real (fechas, decisiones, tareas) debe completarlo el grupo: no se inventan registros de reuniones.

## Metodología

- **Marco**: Kanban liviano con iteraciones semanales (adaptación de Scrum para un grupo de 2 personas).
- **Tablero**: GitHub Projects del repositorio, con columnas `Backlog → En progreso → En revisión → Hecho`.
- **Trabajo en ramas**: una rama por funcionalidad (`feature/...`) y Pull Request hacia `main` con revisión del otro integrante.
- **Commits**: mensajes descriptivos en español; cada integrante aporta commits propios.

## Tracking de features, bugs e issues

Usar **GitHub Issues** con las etiquetas `feature`, `bug`, `docs`, `test` y asignar cada issue a un integrante. Cada PR debe referenciar su issue (`Closes #N`).

| Tipo | Ejemplos de issues sugeridos a crear / enlazar |
|---|---|
| feature | Login con JWT y niveles de acceso · Detalle de rutina desde el backend · Panel de administración de usuarios |
| bug | Rutina nueva mostraba "Ejercicio desconocido" hasta recargar · `muscularGroup`/`muscleGroup` inconsistente |
| test | Tests unitarios, de integración y E2E |
| docs | Documentación de API, proposal y deploy |
